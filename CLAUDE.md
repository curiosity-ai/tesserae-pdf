# CLAUDE.md

Guidance for working in this repository.

## What this is

`tesserae-pdf` ships **Tesserae.Pdf**, a [Tesserae](https://github.com/curiosity-ai/tesserae)
(Transpose C#-to-JavaScript) wrapper around [Mozilla's pdf.js](https://github.com/mozilla/pdf.js),
plus a sample gallery that exercises it in a browser. It depends on **Tesserae only**.

```
Tesserae.Pdf/                       the package
  src/PdfJs.cs                      static factory: Viewer() / ViewerChrome() / PageCanvas()
  src/PdfJs.Runtime.cs              loading, asset URLs, worker location, language
  src/PdfJs.Api.cs                  OpenAsync - a document with nothing on screen
  src/Components/                   PdfComponent (lifecycle base), PdfViewer, PdfPageCanvas
  src/Chrome/                       PdfViewerChrome - the ready-made toolbar, panel and search box
                                    (.Toolbar/.Search/.Panel partials, plus styles, icons, elements)
  src/Interop/                      [External] declarations of pdfjsLib and pdfjsViewer
  src/Types/                        [ObjectLiteral] payloads, enums, and the friendly wrappers
                                    (PdfSource, PdfDocument, PdfPage, PdfError, PdfAnnotation, ...)
  src/L10n/                         PdfL10n + PdfL10nStrings - pdf.js's strings through TNT
  build/bundle-pdfjs.mjs            esbuild: pdfjs-dist's legacy ESM build -> what we ship
  buildTransitive/*.targets         copies the bundle into a consuming app's output
Tesserae.Pdf.Sample/                the gallery - a sidebar of features, one page each
  src/App.cs                        sidebar, routing, reflection-based page discovery
  src/Samples/                      one ISample per feature, plus the shared page furniture
  assets/pdfs/                      the fixtures, generated by scripts/make-sample-pdfs.mjs
scripts/make-sample-pdfs.mjs        writes those fixtures - see "The sample documents"
scripts/stage-samples.mjs           stages the Release build into _site/ for GitHub Pages
```

## Build

```bash
dotnet tool update --global Transpose.Compiler
dotnet tool update --global dotnet-serve
export PATH="$PATH:$HOME/.dotnet/tools"

dotnet build Tesserae.Pdf.slnx
```

The first build runs `npm install && npm run bundle` in `Tesserae.Pdf/` via the `BundlePdfJs`
MSBuild target, so node is a prerequisite.

`Tesserae.Pdf/.npmrc` sets `min-release-age=7`, so `npm install` only resolves versions published
more than a week ago - a supply-chain cooldown. It needs **npm >= 11.10.0**; older npm accepts the
key and ignores it silently, so an old client builds as before rather than failing. `npm ci` is
unaffected either way, and `pdfjs-dist` is pinned exactly.

To see the sample:

```bash
dotnet build Tesserae.Pdf.Sample/Tesserae.Pdf.Sample.csproj
python3 -m http.server 5001 --directory Tesserae.Pdf.Sample/bin/Debug/netstandard2.0/tps
```

## pdf.js is bundled, not vendored

Nothing pdf.js-related is committed. `Tesserae.Pdf/assets/` is gitignored and regenerated from the
pinned npm package on every build.

**The bundle step is not a convenience.** Two files have to evaluate in a fixed order and one of
them is only reachable as a module:

- `pdf_viewer.mjs` has zero imports; it destructures `globalThis.pdfjsLib` at its top level, so
  `pdf.mjs` MUST have evaluated first. Two `<script type="module">` tags do not guarantee that
  across a cold cache; one bundle does, because ESM evaluation order inside it is the entry's import
  order.
- Loading them as modules also means the page cannot ask "has pdf.js loaded" without import-map
  plumbing. An IIFE sets both globals synchronously, which is what `PdfJs.IsLoaded` reads.

### The bundle is fetched with `Transpose.Require`

`PdfJs.LoadCoreAsync` asks for the one script through **`Transpose.Require.RequireAsync`**, the
runtime's own loader, rather than injecting a `<script>` or going through Tesserae's `Require`. It
resolves the URL against `document.baseURI` (so the Pages sub-path and a `<base href>` both work),
shares one fetch between concurrent mounts, waits on the element instead of adding a second one if a
host scripted `pdf.js` from `index.html`, and forgets a failed load so a later mount retries rather
than inheriting the failure.

Write it **fully qualified**. `Tesserae.Pdf` is nested inside `Tesserae`, so a bare `Require` binds to
`Tesserae.Require` - the enclosing namespace beats the `using Transpose;` - and compiles silently
against the old loader. It needs `Transpose.BCL` >= 26.8.4275, the first release carrying `Require`.

### Use the `legacy/` build. This is load-bearing.

pdf.js 6.2's **modern** build calls `Map.prototype.getOrInsertComputed` - a stage-3 proposal -
unconditionally, in 35 places across the display API, the worker and the viewer. Chromium 141 does
not have it and nor does any other shipping browser, so every document fails with
`TypeError: this[#e].getOrInsertComputed is not a function`, thrown *inside the worker* and surfacing
as an `UnknownErrorException` that names nothing.

`legacy/` is the same code through Babel with core-js polyfills bundled in, including that one. The
tax is 512 KB of display code instead of 455 and a 1.31 MB worker instead of 1.26. **Re-check this
when the pin moves**: if the modern build stops needing an unshipped proposal, switch back and drop
~110 KB. The `import.meta.url` in the legacy build is inside a Node-only branch, which is why
`define` can erase it and let an IIFE be emitted at all.

### Two files are copied verbatim, and neither can be bundled

- **The worker.** pdf.js constructs it with `new Worker(src, { type: "module" })` - a hard-coded
  literal - so it has to stay a separate module file. Bundled in, it produces a script nothing ever
  loads and a fake worker parsing on the main thread.
- **The sandbox.** `GenericScripting` loads it with a native `import(sandboxBundleSrc)` and reads
  `QuickJSSandbox` off the module namespace, and the sandbox in turn dynamic-imports
  `${wasmUrl}quickjs-eval.js`, which finds its `.wasm` next to itself via `import.meta.url`. Folded
  into an IIFE, all three break.

### pdf.js assets are NOT Transpose resources

`tps.json` declares only the four self-JS resources. pdf.js is packed into the nupkg under `pdfjs/`
and copied into the consumer's output by `buildTransitive/Tesserae.Pdf.targets`. Three reasons it
cannot be a `resources` entry: Transpose emits a `<script>` tag for every `.js` resource (and the
worker and sandbox must not be injected at all); `"outputFormatting": "Both"` renames resources into
`.min.js` variants, and both of those files are found by a name their own loader expects; and the
`files` globs are single-level, so a tree of ~260 files across five folders cannot be expressed.

Two gotchas in the targets file, both inherited from tesserae-monaco's: `$(OutDir)` is empty at
import time, so the destination is computed **inside** the target; and a `ProjectReference` does not
import the referenced project's `buildTransitive` targets, which is why the sample imports the file
by hand - deliberately, so it exercises the copy a real consumer gets.

### The asset URLs must be absolute

pdf.js resolves `cMapUrl`, `standardFontDataUrl`, `wasmUrl` and `iccUrl` **inside the worker**,
against the worker's own location rather than the page's. A relative `assets/js/pdf/cmaps/` is
therefore fetched from `assets/js/pdf/assets/js/pdf/cmaps/` and 404s from a path nobody wrote. Every
asset URL `PdfJs` hands over is absolute for that reason, and the two scripting URLs are absolute
for a *different* reason - see below.

Getting one wrong does not throw: pdf.js warns and renders what it can, so a CJK document comes out
as blank boxes and an unembedded-font document in the wrong typeface. If a document renders oddly,
check the network tab for a 404 under the asset directories first.

## pdf.js is declared, not scripted

There is **no `Script.Write` in this package**. `src/Interop/` declares the global `pdfjsLib` and
`pdfjsViewer` objects with `[External]`, and `src/Types/` declares the `[ObjectLiteral]` payloads
that cross the boundary. Nothing is emitted for an `[External]` type, so a call site compiles
straight to the JavaScript it names and a typo is a build error. Reach for a new declaration, not a
script string.

Rules learned wiring it up, each confirmed by reading the emitted JS:

- **`[Convention(Notation.None)]` on every external type**, or the compiler camel-cases members and
  `pdfjsLib.GlobalWorkerOptions` is emitted as `pdfjsLib.globalWorkerOptions`.
- **A dotted `[Name]` works on a constructor.** `[Name("pdfjsViewer.EventBus")]` with an
  `extern` ctor emits exactly `new pdfjsViewer.EventBus()`. No `[Template]` needed.
- **A cast between two `[External]` types is erased**, which is what lets `IPdfViewerInstance`
  declare the whole viewer surface once while `PdfViewerJs` and `PdfSinglePageViewerJs` carry only a
  constructor: `(IPdfViewerInstance)(object)new PdfViewerJs(options)` emits nothing but the `new`.
- **Never `as` or `is` on an `[External]` type.** They compile to a runtime type test against
  metadata that was never emitted, and throw rather than answering false. A direct cast emits
  nothing.
- **An array of an `[External]` type cannot be a generic type argument.** The compiler materialises
  one by calling `System.Array.type(element)`, which reads `$$fullname` off the element type - so
  `ToTask<IOutlineNode[]>` throws `Cannot read properties of undefined (reading '$$fullname')`
  *before the promise is awaited*. A bare external interface as a type argument is fine (nothing
  materialises it). Await as `object` and cast; `es5.Map<K,V>` is also fine, because it is emitted
  as the global `Map`.
- **Never `await` an `IPromise`** - see `PromiseHelper`, which is the one place a promise becomes a
  `Task`. `Task.FromPromise`'s selector parameter is typed as `Delegate`, so it needs an explicit
  `new Func<object, T>(...)`.
- **A rejected promise arrives wrapped.** The runtime hands the faulted task a `PromiseException`
  whose `arguments` array holds the real rejection, so reading a discriminator off what you catch
  classifies every pdf.js failure identically. `PdfError.FromJs` peels the wrapper off by shape.
- **`?.` on a delegate field emits an invocation of the object itself.** `_l10nObject?.destroy()`
  became `($nc) => $nc == null ? null : $nc()`, dropping the member name, and every teardown died on
  `$nc25 is not a function`. Write the null check out.
- **An `[ObjectLiteral]` emits only the fields actually assigned**, which is what lets one
  `DocumentInitParameters` carry pdf.js's whole option set without an untouched option overriding a
  pdf.js default with a C# zero.
- **A C# array carries `$type`.** Use `Script.ToArray` for anything pdf.js posts to its worker or
  maps over.
- **`byte[]` cannot be handed to `getDocument`** for the same reason - `PdfSource.FromBytes(byte[])`
  copies into a native `Uint8Array`. And a typed array *is transferred* to the worker, so the
  caller's view is detached and the same array cannot be opened twice.
- **Declare pdf.js, not the platform.** `es5.JSON`, `es5.Date`, `es5.Map`, `es5.Uint8Array` and the
  whole DOM come from `Transpose.Core`; declaring one again shadows the real thing. (`es5.Object`
  does *not* appear to be reachable - `PdfAnnotation` exists partly so nothing needs `Object.keys`.)

## pdf.js behaviour worth preserving

These cost a debugging round each. Don't simplify them away.

- **Initial page, zoom, rotation and layout can only be applied at `pagesinit`.** Set earlier they
  are silently dropped - which looks exactly like them working.
- **A fit mode is resolved once, into a number.** A viewer that fitted its width at 600px keeps that
  scale at 1200px, so the component re-applies the mode on resize - and *only* a mode, never a zoom
  the user chose, which it tells apart by the `presetValue` on every scale change.
- **pdf.js does not read a document's page labels.** `currentPageLabel` and `pageLabelToPageNumber`
  answer against labels the host passes to `setPageLabels`, and answer nothing until it has. The
  component fetches and hands them over.
- **A search's running match count carries no state.** pdf.js raises a control-state event for
  Pending when a search starts and another for the outcome when it ends, with count events in
  between *and sometimes after* - so reporting a count as Pending overwrites "found" with
  "searching" a moment after the search succeeded.
- **`AnnotationMode.EnableStorage` makes a viewer's form non-interactive.** pdf.js tests
  `annotationMode === ENABLE_FORMS` exactly. The failure is silent: an annotation layer with nothing
  in it, no warning anywhere.
- **The annotation editor is decided at construction.** pdf.js builds its editor machinery only when
  the viewer is constructed with the editor on, and `isValidAnnotationEditorMode` rejects `DISABLE` -
  so "is there an editor" is a build-time question and "which tool" a runtime one.
- **A scripting sandbox starts for form fields or document actions**, not for scripts. So
  `sandboxcreated` fires for an ordinary AcroForm; it means the sandbox is running, not that anything
  will use it.
- **`sandboxBundleSrc` and `wasmUrl` resolve against different bases** - a module specifier against
  the importing module, and `location.href` respectively - so both are passed absolute. `wasmUrl` is
  absent from pdf.js's own type declarations but is read by the components build; without it the
  sandbox comes up inert and silent.
- **A calculate action only runs for trusted input events.** Setting `input.value` and dispatching
  `change` from script does not trigger it, which is worth knowing before concluding the sandbox is
  broken. Playwright's `type()` does.
- **pdf.js stops calling `translate()` when given a custom l10n implementation** - it assumes the
  object watches the document, as Fluent's DOM localization does. So `PdfL10n` runs its own
  `MutationObserver`, and `pause()`/`resume()` (which pdf.js calls around inserting a layer) suspend
  it. `resume()` has to walk the subtree, or a layer inserted while paused is never translated.
- **A viewer's DOM shape is not negotiable**: a positioned container holding an
  absolutely-positioned scroll host with a `.pdfViewer` child. That is why the component builds its
  own elements rather than taking one.
- **Release order matters.** Tell the viewer to let go of a document *before* destroying the loading
  task; the other order leaves it holding pages of a document that has gone.

## Fixed: a viewer in an animating modal froze the whole tab

Opening a modal containing a pdf.js view used to stop the browser producing frames **for the entire
page**: `requestAnimationFrame` never fired again, `document.timeline` stopped, and every keystroke,
click and screenshot hung until Chromium killed the tab.

It is a compositing problem, and neither pdf.js's fault nor Tesserae's. pdf.js sizes a page's scroll
layer to millions of pixels square; Chromium rasters a layer running a composited transform
animation over its whole subtree rather than the part in view, and picks the raster scale from the
animation. An animation starting at `scale(0)` - a singular matrix - with a layer that big inside it
makes the raster work unbounded.

`PdfComponent.WaitForAncestorAnimationsAsync` holds the view back until no ancestor is mid-animation.
One frame would be enough - the animation is out of the dangerous range by its second - but waiting
for the animation to end also means pdf.js measures a container whose `getBoundingClientRect` is not
being scaled, which is what its sizing reads. Bounded on both sides: an animation reporting an
`endTime` of `Infinity` (a spinner, a shimmer) is ignored, and the loop gives up after a second.

The diagnostic lesson is the more useful half: **a frozen page is not necessarily a busy main
thread.** Ask `page.evaluate` for a rAF count and `document.timeline.currentTime` before assuming a
loop in your own code. If script answers instantly while both are frozen, every main-thread
hypothesis - an observer cycle, DOM thrash, a dispose loop - is a dead end. The Modal sample page is
the regression check.

## The ready-made chrome

`PdfJs.ViewerChrome()` is `PdfJs.Viewer()` with a toolbar around it, built from
[a Claude Design handoff](https://claude.ai/design) that mocked up two arrangements of the same
controls. It does not weaken the "the package draws no toolbar" position in `PdfViewer` - it is a
*composition* of that component's public surface, in the package because every application that wants
a reader was writing the same twelve buttons.

**The colours are Tesserae's, not the mockup's.** Every surface, border, accent, muted and disabled
value in `PdfChromeStyles` resolves to a `--tss-*` variable, which is not a compromise: the mockup's
light palette *is* Tesserae's light theme, value for value - `rgb(255,255,255)`, `rgb(249,250,251)`,
`rgb(224,230,235)`, `rgb(101,103,107)`, `rgb(36,142,250)`, `rgb(235,234,234)` - and its dark accent
and danger are Tesserae's dark ones. So the light chrome is pixel-identical to the comp and dark mode
came free. Only three values have no theme equivalent (the icon-button hover wash, the faint glyph
grey, the segmented track); they are declared as this sheet's own variables at the top so a host can
override them without reaching into rules.

Things that cost a debugging round each, and are worth not rediscovering:

- **The view element must never be re-parented.** The chrome rebuilds its toolbar, rail and panel
  freely, but `.tsspdf-view` is the last child of `.tsspdf-body` and stays there: taking it out of the
  DOM - even to put it straight back - is a teardown as far as `PdfComponent`'s mount observer is
  concerned, and would drop the document on a change of layout. Everything else is inserted *before*
  it.
- **Subscribe to the event bus, not to the viewer's `On*` callbacks.** Those are single slots, so a
  chrome that used them would silently take `OnPageChanged` away from the host. The bus is multicast,
  and it is rebuilt with the viewer, so the subscriptions go away with it and are replayed by
  `Configure` on the next mount.
- **A `:where()` reset, or the toolbar comes out wrong by one pixel and one shade.** `button` does not
  inherit typography, so the sheet needs a reset - and the obvious `.tsspdf-chrome button` scores one
  class plus one type, which beats every single-class rule below it. `:where(.tsspdf-chrome)
  :where(button,input,...)` scores zero and loses to all of them, which is the point.
- **Outline page numbers and open branches are keyed to a position in the walk, not to a row.** Two
  reasons, and each is a bug on its own: the tree is rebuilt (by closing and reopening the panel, or
  switching layout) and answers living on the row objects would go with it; and destinations have to
  resolve while the panel is *closed*, so resolution cannot walk rows that do not exist. `_outlineFlat`
  / `_outlinePages` / `_outlineExpanded` are parallel lists in the order `AppendOutlineLevel` draws.
- **An outline entry's page number takes a worker round trip, and pdf.js will not do it for you.** A
  destination is a name or an array whose first element is *either* a page reference *or* an
  already-resolved index, told apart by its JavaScript type - which is why
  `PdfDocument.GetDestinationPageAsync` asks `Script.TypeOf` rather than testing a C# type. It buys
  the number beside each entry and, more usefully, "which section am I in".
- **Unrendered thumbnail frames need a placeholder aspect ratio.** Without one every stub is the same
  72px box, and a panel whose tiles are the wrong height cannot be scrolled to the right one - opening
  on page 200 of 248 lands nowhere near it, and because the tiles that then come into view are the
  wrong ones, it never converges. Page 1's proportions are applied to every frame and dropped from
  each as its own page arrives, so a mixed-size document is laid out on a guess and corrected rather
  than cropped to the guess. The ratio is written as `612 / 792`, two integers, because a computed
  decimal goes through a locale and CSS does not accept `0,77`.
- **The "no matches" appearance may only come from a control-state event.** "The count is still zero"
  is what every long document looks like for its first few hundred milliseconds.
- **pdf.js raises nothing when page labels are applied**, and until they are, `currentPageLabel`
  answers null even for a document that has them - so a toolbar reading it at `pagesinit` shows "1"
  for a page the document calls "i" and never learns otherwise. `PdfViewerEvents.PageLabelsApplied` is
  this package's own event, dispatched by `PdfViewer` for that. With labels in play the page box holds
  a label, so the total reads `(11 of 12)` rather than `of 12` - pdf.js's own viewer does the same,
  and "9 of 12" beside a box reading 9 would be a lie about both halves.
- **`PdfFindControllerJs.pageMatches` is the only way to learn *which* pages a search hit** - the
  events carry totals. It is sparse while a search runs (a page pdf.js has not read has no entry,
  which is not the same as no matches), so read it per report rather than accumulating. Typed through
  `es5.Array`, which is emitted as the global `Array`, so nothing is materialised and no `$type` is
  expected on what pdf.js hands back.
- **`CSSStyleDeclaration` has no `aspectRatio`.** `setProperty("aspect-ratio", ...)` /
  `removeProperty`. Several other modern properties are missing the same way; reach for `setProperty`
  rather than adding a declaration.
- **The SVG glyphs are `innerHTML`.** They are compile-time constants in `PdfChromeIcons` with no
  interpolation, which is what makes that safe here and not in general; the alternative is about two
  hundred `createElementNS` calls for the same pixels. A font glyph cannot be stroked at 1.75px on a
  16px box, which is why they are drawn rather than typed.

## The sample documents

`scripts/make-sample-pdfs.mjs` writes the six PDFs the gallery opens, by hand, with no dependencies.
They are generated rather than downloaded so the repository owns its fixtures: each exists to
exercise something specific, the licensing is trivial, and a failing page can be answered by reading
what the document actually contains.

| Fixture | What it is for |
| --- | --- |
| `sample-outline.pdf` | 12 pages, a three-level outline with bold/italic/coloured entries, named destinations, roman-then-decimal page labels, full metadata, and "tesserae" on pages 3, 7 and 11 - so a search count of 3 is a real assertion |
| `sample-images.pdf` | three pages of embedded `DeviceRGB` images, for the render and thumbnail pages |
| `sample-cjk.pdf` | a CID font with no embedded font file, so pdf.js must fetch `cmaps/UniGB-UCS2-H.bcmap` - the `cMapUrl` regression test |
| `sample-forms.pdf` | an AcroForm: text fields, a multiline field, a checkbox, a dropdown |
| `sample-scripting.pdf` | an AcroForm whose total is computed by an `AFSimple_Calculate` action, with `/AcroForm /CO` and a document-level open script |
| `sample-protected.pdf` | RC4 40-bit encryption, user password `tesserae`, denying print and copy - the only fixture whose permissions come back as a list rather than null |

Two traps if you edit it. **Every parenthesis in an embedded script has to be backslashed**, because
PDF's own string delimiters are parentheses - one miscounted closer ends the string early, and
pdf.js reports `Illegal character: 41` from its lexer with no hint that a script is involved. Route
script text through the `escape()` helper rather than escaping by hand. And **permission bits have
to be coherent**: granting high-quality print while denying print is legal and reads as a bug in the
permissions page rather than in the fixture.

Regenerate with `node scripts/make-sample-pdfs.mjs`. The PDFs are committed, so a change to the
script means committing them too.

## The sample gallery

Shaped like Tesserae's own and tesserae-monaco's: a sidebar of features, one page per feature, and a
route per page (`#/view/Document%20Viewer`) so any of them can be linked to or loaded straight into a
browser check.

**Adding a page is adding a class.** `App.cs` finds every `ISample` implementation by reflection and
reads its `[SampleDetails]` for the group, the order inside it and the sidebar icon. The class name
is the page name and the route - `OutlineAndNavigationSample` becomes "Outline and Navigation".

Two things this depends on, both easy to break:

- **Reflection has to be emitted inline.** `tps.json` carries
  `"reflection": { "disabled": false, "target": "inline" }`. With the metadata in a separate
  `.meta.js` the discovery finds nothing and the sidebar comes up empty.
- **Pages are built lazily and torn down on navigation.** `Defer` builds a page when it is opened,
  so one visit creates one page's viewers rather than every page's at startup - and leaving a page
  unmounts them. That is a feature: it exercises the components' teardown on every click.

There are 22 pages in three groups: **Viewer** (the component and everything it does), **Pages** (the
headless half - render, thumbnails, text, metadata, character maps) and **Runtime and hosting**
(loading, modals, remount, several documents, save, scripting, localization).

## Verifying changes

`dotnet build` proves it compiles, not that it works. Nearly every pdf.js failure is a runtime one -
and, worse, a *silent* one: a wrong asset path, a wrong annotation mode and an inert sandbox all
render something rather than throwing. So drive the sample in a browser (Chromium is preinstalled at
`/opt/pw-browsers/`, and `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` is set - do not run
`playwright install`).

Habits that each save a wasted round:

- **Poll, don't sleep.** Pages arrive from the worker, so wait on
  `document.querySelectorAll('.pdfViewer .page').length > 0` rather than a timeout. Canvases are
  lazier still - only the pages in view are painted, so a 12-page document shows 2 canvases and that
  is correct.
- **Watch the network tab, not just the console.** The document should be fetched once and the worker
  once. A second worker fetch, or a 404 under the asset directories, is the symptom for a whole class
  of silent breakage. "Setting up fake worker" in the console is the same class.
- **Two buttons can read the same word.** The sidebar has a nav entry per page, so a page whose own
  button says "Search" has two matches - scope to the one inside the page, or click the last.
- **Type, don't assign.** A form field's calculate action only runs for trusted events; setting
  `.value` from script changes the field and nothing else.
- **`.tss-textblock` is the selector for the gallery's own text.** A bare `querySelectorAll('*')`
  also matches the injected `<style>`, whose `textContent` is 170 KB of CSS.
- **A frozen page is not a busy main thread** - see the modal section above.

Expected console noise, neither of which is a failure: `Cannot load system font: STSong-Light` on the
CJK page (the whole point of the standard-font directory), and a run of
`getHexString - ignoring invalid character` on the Progress and Errors page, where "Not a PDF at all"
deliberately hands pdf.js an HTML file.

Build in **Release** at least once before shipping: Transpose selects `.min.js` resources only there,
so a Debug-only pass does not prove the minified resource set is wired up. And verify the GitHub
Pages sub-path by staging a Release build into a directory named `tesserae-pdf/` and serving its
*parent* - serving the staged folder at the root tests nothing, because a leading-slash regression
only shows up one directory down.

**Check the packaged consumer separately from the sample.** The sample imports
`buildTransitive/Tesserae.Pdf.targets` by hand and so resolves the *repo* bundle
(`Tesserae.Pdf/assets/js/pdf`); the branch that resolves `../pdfjs` inside a restored package is
never exercised by anything in this repository. Pack, drop the nupkg in a local feed, and build a
project whose only reference is the package:

```bash
dotnet build Tesserae.Pdf/Tesserae.Pdf.csproj -c Release
mkdir -p /tmp/consumer/localfeed && cp Tesserae.Pdf/bin/Release/*.nupkg /tmp/consumer/localfeed/
# ... a csproj with a single PackageReference to Tesserae.Pdf, and one line of C#
dotnet build -v n | grep 'Tesserae.Pdf: copied'
```

The log line should name the package directory, not the repo one, and the output should hold 286
files under `assets/js/pdf`. Serving it and loading a document is the last link in the chain that
nothing else covers.

## Publishing the sample to GitHub Pages

`.github/workflows/pages.yml` builds the sample on every push to `main` that touches the package or
the sample and pushes the result to the `gh-pages` branch. Modelled on tesserae-monaco's workflow of
the same name, with this repo's build steps.

**The Transpose output folder is the site.** `tps.json` emits an `index.html` that pulls every script
with a relative path, `Tesserae.Pdf.targets` copies pdf.js in beside it, and the sample's own
`_CopySamplePdfs` target copies the fixtures - so `scripts/stage-samples.mjs` only copies that folder
to `_site/`, drops the compiler's `.tps-manifest.app.json`, and writes `.nojekyll`.

Four things make the sub-path work, none of which needed a change: nothing is absolute (keep it that
way - a `<base>` tag is a bug, not a fix); the bundle finds its own worker from
`document.currentScript.src`; routing is hash-based, so Pages needs no rewrite rule; and `.nojekyll`
stops Jekyll eating paths beginning with `_`.

The NuGet pipeline (`.azure-devops/build-nuget-transpose.yml`) is what ships the package; Pages only
publishes the gallery.
